## The window is the test

During a Type II window, every control has to run every time. Put each one on a shared calendar with an owner and a backup. The [year-round calendar](../plan/observation-calendar.md) gives a starting layout.

## Running an access review

1. Export the current, dated user list from each in-scope system.
2. Send each list to the system owner with a one-week deadline.
3. The owner marks each account keep or remove, and checks that permissions match the person's role.
4. Remove what's marked, with a ticket for each removal.
5. File the lists, marks, tickets, and sign-off together, using the [access review template](../templates/access-review.md).

The most common finding is a departed person's account, still active in a tool nobody thought of. Check that your departure checklist covers every system in the inventory.

## Running a tabletop

Once a year, gather the incident response team for an hour and talk through a scenario, such as "A customer emails to say their data appeared on a public forum." Who's called? Who decides to tell customers? Where are the logs? Fix what was slow or unclear. The notes, attendee list, and follow-up tickets are the evidence for [INC-03](../controls/controls-map.md#incidents).

## When something changes

- **An owner leaves:** reassign their controls the same week.
- **A new system arrives:** add it to the inventory, access reviews, departure checklist, and vendor list.
- **A new vendor touches customer data:** review it before signing.
- **A control changes,** say to a new device management tool: record the date, keep evidence from before and after, and tell the auditor.

## Exercise

Create the shared calendar with every recurring control, each with an owner and a backup. Book the next quarterly access review, and book a tabletop on a scenario from your risk register.
